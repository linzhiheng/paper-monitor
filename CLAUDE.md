# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this project does

Daily academic paper monitoring pipeline written in R. It fetches RSS feeds from geophysics journals, scores each paper for relevance using an LLM, and writes a Markdown digest to an Obsidian vault. Run via `Rscript Paper_Monitor.R`, an interactive menu-driven CLI (a Shiny GUI was tried first and abandoned as impractical).

## CLI tool

`Paper_Monitor.R` is the sole entry point — a terminal CLI (`Run pipeline now` / `Manage RSS feeds` / `Manage recommendations` / `Settings`) built on top of the existing `R/` layer functions, no new pipeline logic. Settings groups Researcher profile, LLM settings, and Output settings. Navigation pages use the shared `R/cli_ui_layer.R` format: numbered entries select domain items, while only the contextually available letter commands perform system actions (`a` Add, `b` Back, `n`/`p` pagination, `s` Save, etc.); `q` exits only from the main menu. Text, date, API-key and confirmation prompts remain compact. The input primitives read stdin directly rather than using `menu()`/`readline()`, since those require `interactive()==TRUE` which plain `Rscript` doesn't have.

- `Rscript Paper_Monitor.R --run` skips the menu entirely, runs the pipeline once via `action_run_pipeline()`, and exits — for cron/scheduled invocations.
- On every launch (menu or `--run`), `check_llm_status_on_startup()` reads `config/llm_config.json` and, if a backend is configured, calls `test_llm_connection()` (`R/llm_layer.R`) and prints the result. In interactive mode a missing/failed connection just prints a warning and still opens the menu (so the user can fix it via "LLM settings"); in `--run` mode it aborts immediately with an error before the pipeline runs, since there's no menu to fall back to.
- In interactive mode, `action_initial_setup()` automatically opens before the main menu when any required first-run setting is missing: a configured LLM, at least one enabled RSS feed, a valid researcher profile, and an existing output folder. It directly opens the first missing step (LLM first for a wholly empty setup), skips completed steps, and advances after each saved step. Its top-level step pages use `c` Cancel initial setup to return to the main menu; `b` remains reserved for real back navigation inside a nested page. Completed steps are saved immediately. The main page retains an `i` Initial setup action for reviewing any setup at any time. `--run` never launches this helper.
- On startup, before loading any package, `Paper_Monitor.R` checks `REQUIRED_PACKAGES` with `requireNamespace()`; if any are missing it lists them and asks to install (`y`/`N`), installing on yes or exiting cleanly on no/EOF. There is no `.Renviron` step — API keys live entirely in `config/llm_config.json` (gitignored), not environment variables.
- All root-level JSON/Markdown config and state files (`feeds.json`, `feed_status.json`, `llm_config.json`, `llm_backends.json`, `output_config.json`, `research_profile.json`, `template.md`) live under `config/`, not the project root. The shared `CONFIG_DIR <- "config"` constant (`R/config_layer.R`) is the single source of truth for the directory name — every path reference in `R/` and `Paper_Monitor.R` builds on it via `file.path(CONFIG_DIR, ...)`. `recommendations.csv` (CSV, not JSON/MD) and the generated `Daily_Papers_*.md` digests (written to the user-configured Obsidian vault folder, not the repo) are unaffected and stay where they were.

### 1. RSS source management

- Feeds live in `config/feeds.json` (fields: `journal`, `rss_url`, `parser`, `parser_arg`, `enabled`); `get_papers()` only processes rows where `enabled == TRUE`.
- Per-feed health status (success/failure, item count, timestamp) persists to `config/feed_status.json` on every real run, so the menu can show last-run status without a fresh fetch.
- A generic RSS fallback parser (`extract_rss_generic`, standard title/description/link/pubDate fields) covers feeds that don't match one of the 4 specialized parsers (AGU/Springer/EGU/RoyalSociety); the feed list shows which type (specialized vs. fallback) each feed uses. New non-standard formats still require a developer to write a dedicated parser — no auto-generation.
- "Test-fetch a feed" runs the matching parser against the URL and previews the first N parsed items without saving — `test_fetch_feed()` in `R/rss_layer.R`. Its result is rendered as a standard fine-line CLI page with a Back action.
- "Add a new feed" starts with the RSS URL only. It downloads the XML once, derives a suggested journal name from the RSS/Atom feed title, then runs all 4 specialized parsers and the generic fallback against that in-memory document. A deterministic quality score rewards parsed title, URL, date, abstract, DOI, authors, and item count; Generic wins a quality tie because it is the safest fallback. The CLI renders the recommended parser's preview inside its standard fine-line confirmation page and lets the user confirm/save, edit the journal name, choose another parser without re-downloading, or discard. New feeds use the confirmed journal name directly and do not need a parser-arg override.

### 2. Researcher profile management

`config/research_profile.json` has the original 15 long-term fields plus `must_read_scope` and `must_read_focus`. Legacy 15-field profiles normalize in memory to `research_direction` with a null focus and are not rewritten until an explicit save. Partial upgrades and inconsistent focused objects are invalid. The "Researcher profile" menu (`action_research_profile()` in `Paper_Monitor.R`) supports full drafting, a short scope/focus-only update, and manual editing:

- **View full profile (raw JSON)** — pretty-printed dump, no editing.
- **Draft new profile with LLM** (`action_draft_profile()`) — a guided, in-memory interview rather than a one-shot free-text prompt. Before any LLM call, the user selects English, Chinese, or Japanese; that selection requires the LLM's questions, inferences, options, and summaries to use the chosen language, while the surrounding CLI remains English and the final JSON retains English scientific terminology. It uses all enabled RSS feeds' journal names and URLs only as a tentative opening scope, which the user can correct; with no useful RSS context it starts from zero. The LLM returns exactly one question plus its current inference and 2-4 recommended answers at a time; the CLI renders numbered options, accepts a number or free-text answer directly at the input prompt, and offers `f` to summarize, `r` to restore and revise the preceding question, and `c` to discard (the legacy `/finish` and `/cancel` inputs also work). A revision restores the original question and options without another LLM call, then regenerates later questions from the corrected answer. It starts narrowing follow-ups from question 6, strongly prefers a summary after question 8, and only permits additional questions after question 12 for essential missing facts; it is forcibly summarized after 15. The user confirms the resulting understanding, may add free-form corrections and re-summarize, then reviews the generated JSON draft before explicitly saving or discarding it. Interview responses are not persisted, and a failed LLM/protocol call is retried once before the interview ends without touching the existing profile. Final drafts use at least 4096 output tokens and are checked for the required fields, valid core-interest weights, and matching topic-alias keys before they can be saved. If no backend is configured, the CLI directs the user to LLM settings instead of printing an external-chat prompt.
- **Manually edit current profile** / **Create profile manually** (`action_manual_edit_profile()` and field-specific editors `edit_string_list()`/`edit_core_interests()`/`edit_topic_aliases()`) — a field-by-field editor with no LLM involved at all; edits stay in memory until the user explicitly picks "Save" in the field list (an explicit "Discard" abandons everything).
- The long-term interview is followed by an additional-directions prompt, a deterministic must-read scope choice, and (for `focused`) a separate 3–8 question focus interview. Focused scope constrains only `must_read`; it does not redefine ordinary recommendation relevance. The short update flow changes only the two must-read fields.
- `call_llm()`/`call_ollama()`/`call_claude()`/`call_deepseek()`/`call_openai_compatible()` (`R/llm_layer.R`) all take an optional `simplify` parameter (default `TRUE`, unchanged for the paper-scoring path) so the profile draft can request `fromJSON(..., simplifyVector = FALSE)` and get back the same nested list-of-lists shape `read_json_config()` uses everywhere else, instead of `core_interests` collapsing into a data.frame.

### 3. LLM provider selection

- Provider picker: Anthropic, OpenAI, DeepSeek, Ollama, and Custom OpenAI-compatible. Cloud providers use built-in current model suggestions plus a Custom model name option: Claude Fable/Opus/Sonnet 5 and Haiku 4.5; GPT-5.6 Sol/Terra/Luna; and DeepSeek V4 Pro/Flash. Ollama instead asks directly for the locally installed model name. Anthropic retains its optional Batch API mode; Ollama defaults to `http://localhost:11434/api/generate` and exposes endpoint editing only as an advanced setting; Custom OpenAI-compatible is the sole path that asks for a Base URL.
- Provider selection fixes the corresponding Base URL and creates a compatible existing `backend` value (`claude`, `ollama`, or `openai_compatible`) in `config/llm_config.json`; an additional `provider` field makes the chosen service explicit. Existing configs without that field are inferred from their backend and URL.
- The review flow tests the connection by default. A successful test saves the config; on failure, the user can edit it, discard it, or explicitly save it to test later. Existing configs show the current Provider/model and offer Keep, Reconfigure, or Test connection.
- API key storage: plaintext in `config/llm_config.json` (user's explicit choice, prioritizing convenience). This file is `.gitignore`d — never committed.
- Switching backends in the menu always restores remembered per-backend defaults (model/key/url/etc.) from `config/llm_backends.json`, keyed by `backend_key` — there's no "is this the same backend type as before" gate; each backend simply has its own remembered settings.
- All four backend call functions (`call_ollama`/`call_claude`/`call_deepseek`/`call_openai_compatible`) parse their raw response text through `parse_llm_json_text()` (`R/llm_layer.R`), which tries three candidates in order and keeps the first that parses: (1) the raw text with quotes that cannot be structural closings escaped by `escape_inner_json_quotes()` — this preserves typographic “ ” quotes, which are legal inside string values; (2) the historical `clean_llm_json_text()` path, which strips a markdown code fence (` ```json ... ``` `), trims stray prose outside the first `{`/`[` through the last `}`/`]`, normalizes "smart" quotes to plain ASCII, drops trailing commas before a closing bracket, and escapes raw control characters (literal newline/tab/CR) inside string literals via `escape_control_chars_in_strings()`; (3) the clean path with inner quotes escaped. The escaping step is a no-op for well-formed JSON, and a repaired parse prints one line naming the label. The historical path alone is lossy: rewriting “ ” into `"` inside a string value invalidates JSON that was previously valid, so it is now only a fallback.

### 4. Output location

- Output folder is stored in `config/output_config.json` (`output_folder`, `filename_pattern`, `max_papers`, `recommendation_threshold`); the CLI prompts for a folder path and offers to create it if missing (no GUI folder picker possible in a terminal).
- The Output settings page (`action_output_settings()` in `Paper_Monitor.R`) shows all 4 fields as a numbered list with current values; selecting a field edits and saves just that one, while `b` returns — editing one setting doesn't require re-confirming the others.
- Filename pattern's `%s.md` suffix (date substitution + extension) stays fixed; only the prefix before it is interactively editable from the Output settings menu.
- `max_papers` caps how many newly-discovered (deduplicated) papers get sent to the LLM for scoring in a single run; configurable from the Output settings menu (default 25), read by `run_daily_papers_from_config()` in `R/pipeline_layer.R`.
- `recommendation_threshold` is the minimum score a scored paper needs to be included in the written digest (`build_digest_lines()` in `R/output_layer.R` filters on it); configurable from the Output settings menu (default 50).
- The per-paper Markdown block is driven by `config/template.md` (tracked in git — not a secret), using `{keyword}` placeholders (`{title}`, `{score}`, `{category}`, `{matched_topics}`, `{journal}`, `{authors}`, `{date}`, `{link}`, `{reason}`, `{tldr}`, `{abstract}`, `{doi}`, `{paper_number}`) substituted per paper by `render_paper_block()` in `R/output_layer.R`. `tldr` is LLM-generated alongside `score`/`category`/`reason` — `build_paper_prompt()` (`R/prompt_layer.R`) asks for a 1-2 sentence summary of the abstract itself (not a relevance judgment), distinct from `reason`, which explains the relevance score. `paper_number` is the paper's 1-based position within that day's digest (not a global/persistent ID) — it's used to give each paper's Reader Review a unique Meta Bind property name (`paper-{paper_number}`) so the Decision inputs of different papers in the same file don't collide; it resets to 1 each run, which is fine since each run writes its own Markdown file with its own frontmatter. The Reader Review callout only carries `Paper_id` (the DOI) and `Decision` — a Meta Bind `INPUT[inlineSelect(...)]` bound to `paper-{paper_number}` — no separate rating/recommend/notes fields. If `template.md` is missing, `read_paper_template()` falls back to `DEFAULT_PAPER_TEMPLATE_LINES` (same file's content) so a fresh checkout still works. Unrecognized placeholders are left as literal text and trigger one `cat()` warning per run rather than failing. The digest header is a YAML-frontmatter-style `---`-delimited properties block (`Generated:` / paper counts) rather than a Markdown heading — it's aggregate data, not per-paper, and is not templated.

### 5. Recommendation history management

- `recommendations.csv` accumulates every scored paper across runs (append-only, deduplicated by DOI — `load_history()`/`update_history()` in `R/scoring_layer.R`); the CLI's "Manage recommendations" menu is the only way to inspect or prune it.
- Shows summary stats (total, by `category`, by `processed_date`) plus a paginated browse view with full per-row detail, and supports deleting everything, one category at a time, or by `processed_date` (today / yesterday / a specific `yyyy-mm-dd` date, validated against that exact format) — all behind a confirmation prompt.
- In `.process_sequential()` (`R/scoring_layer.R`, used by Ollama/Claude-direct/DeepSeek/OpenAI-compatible backends — not the Claude Batch path), a paper whose LLM call fails (JSON parse failure or thrown exception) is retried once after a 15-second wait; if the retry also fails the paper is skipped and never appended to `results_df`, so it's never written to `recommendations.csv` and will be re-fetched and re-scored on the next run.
- Sequential and Batch results use the same semantic validator. Categories are derived from the final score; a false or unconfirmed focused match caps the score at 89, while a true match never adds points. History stores scope/focus provenance and creates a one-time `recommendations.pre-must-read-scope.csv` backup before expanding an older schema.
